  The one idea everything hangs on

  The app has exactly one screen that matters: Now. It shows one task, full
  width, themed in that task's color, with a clock running. Every other screen
  exists only to feed Now or to look back at it. You never see a list of open
  tasks while a task is active. You never see a dashboard between finishing one
  and picking the next. Done is one key, and that key opens the picker.

  The tension in your brief resolves cleanly: "every action is gated by a task"
  and "no gates on when or why" are compatible if the gate is attribution, not 
  permission. Nothing is ever forbidden. Every action just has to carry a task
  id. If you start doing something with no task active, the app creates the task
  from the action instead of blocking you.

  Levels, never mixed

  Four levels, each its own view, each with one verb:

  ┌────────┬─────────────────────────────────────────────────────┬──────────┐
  │ Level  │                   What lives here                   │  Only    │
  │        │                                                     │   verb   │
  ├────────┼─────────────────────────────────────────────────────┼──────────┤
  │ Noise  │ raw captures: pastes, transcripts, links, pane      │ extract  │
  │        │ output                                              │          │
  ├────────┼─────────────────────────────────────────────────────┼──────────┤
  │ Items  │ tasks, to-knows, deferred motivations               │ pick     │
  ├────────┼─────────────────────────────────────────────────────┼──────────┤
  │ Now    │ the single active task + its subtasks               │ finish   │
  ├────────┼─────────────────────────────────────────────────────┼──────────┤
  │ Review │ done log, counts per day                            │ read     │
  └────────┴─────────────────────────────────────────────────────┴──────────┘

  // everything is a typed item with metadata; collections are just filters
  item = { id, type, meta, links }

  noise      = { id, type:'noise', meta:{ body, source:'clipboard'|'pane'|'cli',
  at } }
  task       = { id, type:'task',  meta:{ title,
  state:'open'|'active'|'done'|'split', parent, from: noiseId } }
  know       = { id, type:'know',  meta:{ question, answer, state } }
  motivation = { id, type:'motivation', meta:{ title, why, unlockAt, from:
  learnRunId } }
  action     = { id, type:'action', meta:{
  verb:'write'|'read'|'run'|'ask'|'split', taskId, at } }

  links = [ { rel:'from', to:'noise_123' }, { rel:'child', to:'task_456' } ]

  The generic selector searches items with a type filter. Same widget
  everywhere. In Now it's scoped to subtasks of the active task, in Items it's
  everything pickable, in Noise it's raw bodies.

  The loop that produces checkmarks

  session = { taskId, startedAt, lastActivityAt, breaks:[{ at, dur }] }

  rules = [
    { when: 'idle > 3min',                    then: 'unset task, return to 
  picker, notify' },
    { when: 'active > 15min && breaks == 0',  then: 'reset task, open split 
  prompt' },
    { when: 'done',                           then: 'log action, open picker 
  immediately' },
    { when: 'action with no active task',     then: 'create task from action, 
  activate it' },
  ]

  The 15-minute reset is the engine, not a punishment. When it fires, the prompt
  is not "pick something else" but "what is the smallest piece of this you can
  finish in 5 minutes?" The answer becomes a child task and the parent gets
  state split. Tasks shrink every time they resist you, so the day naturally
  fills with finishable pieces.

  The picker has no priority field. Default sort is oldest-first within
  smallest-first, plus one key that deals you a random task. Since nothing is
  off the table, there is nothing to deliberate. Pick, finish, pick.

  The review level counts finishes. Hours never appear anywhere. The only number
  the app shows you is how many things you checked off today.

  The funnel and the deferral valve

  Capture is a shell command and a tuios pane grab, both landing in Noise with
  zero structure. Extraction is itself a task called "triage noise" that gets
  picked like anything else, so even cleaning the inbox earns a checkmark. Each
  extracted task keeps a from link back to the noise it came from, so you can
  always see why it exists.

  The "learn about X for Y" runs are a separate command. Output goes straight to
  motivation items with an unlockAt. The picker's filter excludes them until
  that time. They have their own Later view where you can read but not activate.
  Promoting one early is possible but logged as an action, so it shows up in
  review as a conscious choice rather than a drift.

  What makes it feel like a mode

  The whole palette derives from the active task's id, so switching tasks
  changes the color of every border and bar. Idle detection reads your own pane
  activity through tuios events, and the nudge goes to the pane you're actually
  in. Starting a Now session can also announce itself as tuios agent state, so
  other agents in your fleet can see what you're on and address their mail to
  that task.

  First slice to build

  Now screen, picker, done key, the two timers, a JSONL store. Nothing else.
  That slice alone proves whether the loop changes your day. Noise, learn runs,
  and theming come after, each as a task picked inside the app itself.

  How it works

  poll_slack = {
    server: env.NOW_SLACK_MCP ?? 'slack',          // slack | slack-no-dms | 
  glean | runlayer | runlayer-plugin
    tool:   first of [ 'slack_search_public_and_private', 'slack_search_public',

  block becomes one noise item per message, with slack.thread when thread_ts
  differs from ts and the permalink as ref. A prose result becomes one item per
  paragraph, keyed by a content hash so repeats dedup.

  6. End of day. Header reads 1 pickable · 11 done today · 14 noise. That count

⏺ The short version: the multiplexer is the physical substrate, the task is the
  label, and agents are workers whose output comes back through the funnel. None
  of them becomes a new level in the app.

  The mapping

  ┌─────────────────────┬────────────────────────────┬─────────────────────┐
  │   Terminal thing    │     What it is to now      │      Never is       │
  ├─────────────────────┼────────────────────────────┼─────────────────────┤
  │ Pane or window      │ where work physically      │ a task, or a thing  │
  │                     │ happens; its id is a ref   │ you pick            │
  ├─────────────────────┼────────────────────────────┼─────────────────────┤

  tuios already emits the events this needs: prompt, command-started,
  command-finished, agent-state, agent-activity (prompt, tool call, result,
  finished turn), notification, attention. A subscriber in now turns them into
  the rows above. That also fixes two rough edges at once: any pane in your
  session counts as activity, and the idle nudge can go through tuios instead of
  a toast.

  What one agent interaction feels like

  pick "fix flaky login test"      → window title becomes the task; panes in it 
  are attributed to it
  type a prompt in the claude pane → event prompt     → action{ask, task:t1}, 
  activity touched
  wait                              → 3 min idle      → task put back, picker. 
  you pick something else
  agent finishes                    → event agent-state done
      task t1 is not active         → child task "read reply in pane cbde" under
  t1, pickable
      task t1 is active             → Now screen shows one line: "agent replied"
  agent asks a question             → agent.needs_input → same rule: child 
  "answer claude in pane cbde"

  The important consequence is that waiting on an agent is never a thing you do.
  The idle rule throws you back to the picker, the agent's completion arrives
  as a small finishable item, and the day's checkmark count goes up instead of
  you babysitting a spinner. Fan-out works the same way: five agents on five
  tasks produce five small "read reply" items, each linked to its parent and its
  pane.

  Agent output is the one place where extraction can be automatic. Slack
  messages and PR notifications need you to decide what the task is. An agent
  response already knows its task and its pane, so the child task writes itself.
  Prompts with no active task fall under the attribution rule from the brief:
  the prompt creates the task, it does not get blocked.

  Sessions and windows stay thin. A task may record where it was last worked, so
  picking it can focus or spawn that window. That is the "Context" abstraction
  from your brief made concrete, and it is the version of theming that matters
  more than colors: pick a task and the terminal flips to its place. I would not
  go further than that pointer. Modeling panes as items would mix the physical
  layer into the Items level, and the app never shows a pane list for the same
  reason it never shows a dashboard.

  The learn-for-later prompts fit here too. now learn "x for y" would spawn an
  agent pane, tag it as throwaway, and route its finished turn into motivation
  items with an unlock time instead of into noise. Nothing from that pane ever
  becomes pickable today.
